# Native I/O end-to-end investigation — 2026-11-09

A separate [instrumented IOPS report](native-io-iops-2026-11-10.md) records physical read/write/total completions and native read SQEs; its observations and observer-cost qualifications are separate from these untraced latency results.

Keep mmap as the default; buffered/direct remain opt-in. The constrained CPU experiments show end-to-end gains, while resident experiments generally favor mmap. The current evidence supports controlled CPU experiments and concrete follow-up work, not a general production rollout or GPU claim. The port preserves the engine's existing seeded neighbor-sampling algorithm; no portable-checksum work is included.

## Earlier exploratory tuning and limits

Old-source binary 1,280-batch default-geometry observations were 43.89/54.87/64.16 s resident and 346.90/65.74/74.52s constrained for mmap/buffered/direct fit→first prediction. They are separate n=1 calibration variants on the old b9aa native build, never pooled with 75ca. During constrained training, buffered/mmap had 1.53M/1.74M pgscan and direct 3.58M native evictions with zero OS scans.

The allocation-churn explanation was experimentally insufficient: at 2 rings/QD 32, multiplier 8 reduced buffered allocations from 7.774M to 72 but training changed only 51.439→50.801 s. Two-ring QD 256 took 51.544 s and native-default 8 rings/QD 256 took 47.621 s. Each is n=1; Python revisions differ. No wakeup/operator cause is established.

Before wider enablement: validate integer configuration and explicitly budget native cache plus parent/workers/model memory; qualify representative production worker concurrency/GPU and the declared compiler. Cache-lifetime reuse and a seeded-reproducibility contract are separate follow-up PRs. Production UUID/neighbor RNG defaults are unchanged.

Coverage is ARM CPU/local NVMe/ext4, 121 GiB host RAM, with no usable GPU. Compiler was installed Rust 1.96.1 rather than declared 1.99.1, recorded as a toolchain override; release qualification on the declared toolchain remains an action item. Items in these LP graphs have no temporal validity columns: the benchmark measures temporal edges, not candidate creation/end-time filtering performance. New upstream LP integration tests separately cover that correctness.

Core/benchmark reader and sampler hot paths match; the 19 native counters are already unconditional in the production core, and the benchmark adds explicit snapshot access rather than per-page profiling work. Python per-batch logical hashing and phase/resource observation overhead is unquantified and may affect relative ratios. Shared instrumentation does not establish cancellation. TT 1/1, LP 3, workers 0 and Torch threads 1 qualify the controlled experiment, not default auto-ingestion performance.

Performance ratios qualify the explicit ARM CPU configuration: workers 0, standalone loading, Rayon 4 and Torch threads 1. They do not establish the best parallel mmap configuration or throughput under the production automatic worker policy. The observed recommendation of 8 workers × 2 Rayon under both scope sizes is a policy observation; no full automatic-worker fit timing or OOM result was established. Before deployment, qualify representative production workloads with their intended worker concurrency and GPU environment; avoid extrapolating the controlled ratios to all production training.

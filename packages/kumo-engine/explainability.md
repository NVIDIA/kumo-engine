# Training and batch prediction explanations

The local Python API retrieves diagnostics already generated by `Trainer.fit()`.
It does not retrain a model. Batch prediction can separately generate diagnostics
for its current inputs with `Trainer.predict(..., explanations=True)`, described
below. Explanation generation can fail without invalidating training or prediction.

## Notebook widgets

Display `training_result.visualize()` to inspect training Evaluation, Training and Explanation views.
The header shows the predictive query.
When the published model was refit on all data, a note says that diagnostics and explanations describe the model before the refit.
Under **Evaluation**, **Metrics** shows the holdout scores of the main metrics, then a table of every recorded metric with its Holdout, Validation and Training values.
Validation and Training values are from the last epoch of the original run.
Baseline rows (random for link prediction; predict zero and predict the mean for regression and forecasting) follow the model rows and are scored on the holdout only.
The **Training** tab holds **Learning Curves** and the **Training Table**.
**Learning Curves** compares training and validation scores across the search experiments that preceded model selection.
The tuning metric opens first, with only the best experiment (the one the final model came from) selected and marked **(best)** in the legend.
Tick other experiments to compare their curves on the same scale, or change the metric.
Each point represents a recorded epoch. Missing scores leave gaps, and epochs from the later refit are excluded.
The widget reads `metric-history.json` from the published bundle or `auto_train_progress.json` from the retained run. The card appears when either source contains training or validation series.
The best experiment is the `version_<n>` that the retained run's `best_trainer.json` names.
Without a retained run, it is the one experiment whose recorded validation score for the tuning metric equals the bundle's; if none or several match, no experiment is marked and all start selected.
A single experiment shows no legend.
The **Training Table** lists the training, validation and holdout splits with their row counts.
Further columns appear only when the facts are recorded: distinct entities (approximate, never above the row count), the positive rate for binary tasks, the target mean for regression and forecasting, and the anchor time range for temporal tasks.
Static tasks show no time column.
The widget reads them from the training table's `split_stats.json` in the retained run, and otherwise row counts and anchor times from the bundle's `manifests/input.json`.

Binary classification adds a **Classification cutoff** card.
Its first row holds the confusion matrix beside a compact cutoff slider.
Its second row holds the ROC, Precision-recall and Cumulative gain curves side by side, and they stack only on narrow screens.
Multilabel ranking and static or temporal link prediction add **Ranking quality by cutoff K**.
It draws one chart per metric family (recall, precision, MAP, NDCG and F1) with the holdout, validation and last-epoch training score at each K, tuning metric first.
Every value is the one in `training_result.metrics`; a family with a single K, or a split with no scores, is left out.

Display `prediction.visualize()` for a batch prediction result to open the batch widget, with the same styling and graph controls on a single page.
It shows the batch, model and snapshot identities, a Cohorts chart with class selection and sampled subgraphs with their recorded predictions.
Cohort charts show average predictions and sampled population shares; a batch has no observed outcomes or evaluation metrics.
An unavailable, disabled, unsupported or failed producer is listed under **Explanation availability**, and the other producer's card still appears.

```python
prediction = trainer.predict(snapshot, explanations=True)
prediction.visualize()

# Reopen a retained prediction run, including its xai/manifest.json:
from kumo.engine import PredictionExplanations
PredictionExplanations.load("/path/to/prediction/run").visualize()
```

Use **Export PDF** to print every chart view on the currently open page, including Metrics on the Evaluation tab or Learning Curves and the Training Table on the Training tab, then choose **Save as PDF** in the browser dialog.
The export preserves the selected explanation and chart controls.
The other tabs are excluded.
If the notebook blocks pop-ups, open the downloaded print page to save it as PDF.
**Export HTML** downloads the complete interactive widget with its current chart and customer selections, including the saved data needed to explore other records offline.
Neither export requires a running kernel after saving.

Call `.html()` on the returned view for self-contained HTML, or `.as_widget()` to request the optional anywidget transport explicitly.
Use `training_result.visualize().save("training-report.html")` to save a portable report with its default chart selections.
`.page(title)` returns that standalone HTML page as a string; `.save(path, title)` writes it to a file.
Open the saved report in a browser without a running notebook kernel.
Snowflake notebooks use the anywidget transport supplied by the runtime, with the same `visualize()` call.
With MLOps on, every tracked fit logs this page as `training-report.html` in its run's artifacts.
The saved notebook snapshot includes the model summary, metrics, default Evaluation charts, the epoch-history summary and the Training Table, followed by “To activate the widget, rerun this cell.”
A batch snapshot shows its identities, availability, default cohort chart and subgraph coverage instead.
Individual subgraphs are omitted from that static snapshot.
Opening either widget only reads retained artifacts; it never starts training, prediction or explanation generation.
Retain the prediction run separately from exported predictions; a bare export cannot supply its explanations.

## Access the selected training run

Capture the result returned by your existing training call:

```python
training_result = trainer.fit(training_table, snapshot=snapshot)
explanations = training_result.explanations
print(explanations.run_root)  # retain this directory to reopen diagnostics
print(explanations.trial_root)  # selected TEST explanation trial
print(explanations.availability)
```

Attachment is lazy: fitting retains paths and generation status, without reading
the artifact bodies or retaining the core trainer. Availability checks file
presence; they do not validate the contents or load graph bodies. The keys are
`gradient`, `cohorts`, and `samples`. Each entry has `available`, `path`, `reason`,
and `generation_failure`. Missing artifacts are never zero-valued explanations.
A failed generation can still leave readable partial artifacts.

When unavailable, `reason` distinguishes known disabled or failed generation,
model-only loading, and an unknown cause. Historical files do not establish why
an artifact is absent. Training generation status captured during fit is not
archived by this API; reopening training runs reports unknown causes for missing
artifacts.

To reopen a retained run without training:

```python
from kumo.engine import TrainingExplanations

explanations = TrainingExplanations.load("/path/to/retained/run")
```

Supply the run containing `models/<task>/automl/best_trainer.json`. The loader
requires one selected-trial record and rejects ambiguity. It uses the selected
original trial and its recorded `config.json` train/validation refit state.
Missing or invalid refit state raises `InvalidRunError`; directory presence
alone does not select a refit. TEST explanations use `_refit_trainval` when
recorded and do not select `_refit_full`. Copied runs resolve selection within
the supplied run, rather than following an old absolute path.

Published model bundles omit these diagnostics. `Trainer.load(bundle)` leaves
its result's explanations unavailable with reason `model_only`; retain and
open the training run separately. A model stored or registered through MLOps
also contains only its bundle; retain `explanations.run_root` separately.
Clearing that scratch run removes access to these diagnostics.

## Gradient scores

```python
if explanations.availability["gradient"].available:
    scores = explanations.gradient_scores()  # kumoapi GraphGradientScore
    frame = scores.to_pandas()  # table, column, score
    figure, axis = explanations.plot_gradient(top_k=20)
    figure.savefig("training-importance.png", bbox_inches="tight")
```

Bars use table-qualified column labels. Returned figures and axes support
customization and saving; plotting never calls `show()`. The explanation
helpers import Matplotlib only when plotting is requested. `pip install
"kumo-engine[plots]"` explicitly requests the plotting dependency. This extra
is currently redundant with core's existing required Matplotlib dependency:
the wider `import kumo.engine` also imports Matplotlib through its training
workflow. Explanation retrieval adds no plotting import, but the complete SDK
cannot yet be used in a Matplotlib-free installation. Decoupling those existing
core imports and dependencies is outside this change.

The training producer normalizes column scores by their global total when it
is positive and writes `scores.csv` with six decimal places. Retrieval preserves
those recorded values, including zero scores and rounding; it cannot restore
unnormalized gradients. Rounded values need not sum exactly to one. Plots do
not apply another normalization or convert scores to percentages.

## Column cohorts

Discover the complete `(table_name, hop, col_name)` keys and class labels first:

```python
print(explanations.cohort_keys())
key = ("users", 0, "age")  # choose a key from the printed output
print(explanations.classes(key))
```

For class-keyed multiclass or multilabel outputs, explicitly choose a label
returned by `classes(key)`:

```python
cohort = explanations.cohort(key, class_name="True")  # use your class label
figure, (prediction_axis, population_axis) = explanations.plot_cohort(
    key, class_name="True")
```

For regression or binary positive-class vectors, `classes(key)` is empty:
omit `class_name`. No missing negative-class vector is fabricated.
`cohort()` returns the shared `ColumnCohorts`
schema; class selection validates the label while retaining its full class
dictionaries. `column_analysis()` returns the validated `ColumnAnalysisOutput`.
The upper plot shows predictions and observed targets when recorded. The lower
plot shows population shares on a separate axis.

Cohort `prediction_score` measures variation between cohorts. It is a different
quantity from gradient attribution. Neither establishes causation. Duplicate
keys, inconsistent classes, nonfinite scores, misaligned lengths, and invalid
population shares raise errors instead of producing misleading plots.

## Sampled graph context

```python
samples = explanations.samples()  # references, without loading graph bodies
for reference in samples:
    print(reference.artifact_id, reference.categories, reference.original_ids)
    if reference.available:
        graph = explanations.sample(reference.artifact_id)  # kumoapi Subgraph
        print(graph.subgraph_store, graph.feature_store)
```

Graphs retain recorded structure, features, optional scores, timestamps, and
aggregated nodes. A reference can exist for a missing graph; check `available`.
`artifact_id` is collector-local. Optional `original_ids` are recorded entity
identifiers organized by sampling category; they are not interchangeable with
collector IDs. Without those mappings, arbitrary original-key lookup is not
available. These bounded samples are training context, not explanations for
every entity. The notebook widget renders these saved graphs interactively.

## Availability and validation

| Training task | Producer capabilities, subject to model and retained outputs |
| --- | --- |
| Binary, multiclass, multilabel classification; regression | Gradient scores, column cohorts, sampled graphs |
| Static or temporal link prediction | Gradient scores and sampled graphs; gradient generation excludes two-tower modules |
| Forecasting | Gradient scores; column cohorts and sampled graphs are not generated by these producers |

The table describes producer eligibility, not a guarantee that a particular run
contains every artifact. `training_job.disable_explain`, model support, failed
generation, sampling, and cleanup affect availability.

Public errors are exported from `kumo.engine`: `ExplanationUnavailableError`
for missing artifacts, `InvalidExplanationError` for malformed data, and
`InvalidRunError` for an invalid or ambiguous retained-run selection. Unknown
cohort keys or classes raise explicit lookup/selection errors. Availability
can change if files are removed after checking it.

The implementation's small fixtures use the shared producer schemas and CSV/JSON
writers from source revision `74465d01`, plus mocked training integration and
headless plotting. Real CPU fits of one binary classification query also run.
Two refit fits in `test_holdout_df.py` check which trial the artifacts describe.
The CPU lifecycle check of the candidate wheel reopens a copied training run in
a fresh process. It verifies that the explanations describe the published refit
model, renders both plots, inspects the sampled graphs and checks broken-run
diagnostics. These checks do not use retained
artifacts from a released v1.0 training run, so released v1.0 artifact
compatibility remains unverified. Website guide
source and publication are maintained separately; this local guide does not
update or publish the website.


## Batch prediction explanations

Enable generation for each prediction call that needs diagnostics:

```python
prediction = trainer.predict(snapshot, explanations=True)
xai = prediction.explanations
print(xai.run_root)  # retain this directory separately
print(xai.run_id)  # recorded prediction run, even after copying the directory
print(xai.availability)  # cohorts and samples
print(xai.coverage)  # observed row/graph counts and selected checkpoint

if xai.availability["cohorts"].available:
    print(xai.cohort_keys())
    cohorts = xai.column_analysis()

if xai.availability["samples"].available:
    reference = next((item for item in xai.samples() if item.available), None)
    if reference is not None:
        graph = xai.sample(reference.artifact_id)
```

The default `explanations=False` skips the extra computation and records
`disabled`. Opting in replays the supplied prediction inputs and snapshot
against the same published checkpoint used for scoring, including after
`Trainer.load()`. It does not reuse training TEST diagnostics or retrain.
Generation starts after predictions have been saved and any configured export
and tracking finish. Supported node tasks process bounded cohorts and sampled
graphs; supported link tasks generate sampled graphs.

Cohort populations describe the producer's bounded sampled prediction prefix,
not the entire batch population. With `B = max(eval_batch_size // 4, 1)`, the
default cohort budget is `max(50 * B, 1000)` rows rounded up to whole batches:
`ceil(max(50 * B, 1000) / B) * B`. A smaller input population processes fewer rows.
Sampled graphs cover up to the first 1,000 prediction rows,
not arbitrary entity IDs or every batch row. Collector-local artifact IDs and
original entity IDs have the same distinction as training samples; repeated
entities at different prediction times are separate prediction rows. This
scope exposes column cohorts and sampled graphs without gradient scores,
RFM summaries, or historical-item APIs. Neither cohorts nor graphs establish
causal effects.

Set independent row limits by passing options instead of `True`:

```python
from kumo.engine import PredictionExplanationOptions

prediction = trainer.predict(
    snapshot,
    explanations=PredictionExplanationOptions(cohort_rows=500, sample_rows=100),
)
```

Each limit must be a positive integer. An omitted limit uses its
default. Explicit limits cap rows exactly, including the final batch, and a
smaller cohort limit does not reduce the sampled-graph limit.

`xai.coverage` is a typed `PredictionExplanationCoverage` value with
`cohort_rows_processed`, `sampled_graphs`, and `checkpoint_path`. Counts describe
the work observed during generation, including failed cohort callbacks;
`None` means unresolved and zero means observed empty. The checkpoint path is
relative to the published model root. These counts remain the generation record
when files are later removed or a run is only partly copied. Check
`availability` and each sample reference's `available` flag for files present now.

Cohorts support binary, multiclass and multilabel classification and regression.
Their predictions have no observed targets for batch prediction. The same
`cohort_keys()`, `classes()`, `cohort()`, and `plot_cohort()` selection rules
apply; the plot omits the observed-target line. Sampled graphs support those
tasks and supported static/temporal link models (HYBRID, ID and SHALLOW_RHS).
Forecasting and multilabel ranking have neither output from these producers.
Support is determined independently of producer success, so an unsupported
capability remains `unsupported` when another producer fails.

Generation errors are logged and recorded as `failed` with
`generation_failure`; completed predictions remain usable. Failed producers'
partial files remain on disk for diagnostics and are unavailable through normal
retrieval. A producer that completed independently remains readable. Presence checks stay lazy;
malformed retained contents raise `InvalidExplanationError` when read, and
requesting absent cohort data or a missing graph raises
`ExplanationUnavailableError`. Sample listing can be empty when no graphs
or selection mappings were retained.

To reopen without running prediction:

```python
from kumo.engine import PredictionExplanations

xai = PredictionExplanations.load("/path/to/retained/prediction/run")
```

Pass the complete engine prediction run root, including its compact versioned
`xai/manifest.json` status and available producer artifacts under
`xai/column_analysis/pred/` and `xai/subgraph_collector/pred/`.
The status records the actual prediction run ID, whether explanations were
enabled, completion state, independent producer outcomes and observed coverage.
Sample membership comes from the saved `strategy_mappings.json`. Unmapped graph
files do not become samples.

Loading requires valid status; an arbitrary artifact directory is rejected.
Disabled, unsupported and failed states survive reopening, including errors
and observed coverage. Copied runs resolve files beneath the supplied root and
keep their recorded `run_id`, even when the directory is renamed. Prediction Parquet
exports, connector reloads, and model bundles do not include these diagnostics.
Keep `xai.run_root` until diagnostics are no longer needed; scratch cleanup
removes them.

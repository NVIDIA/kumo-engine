DiskGraph sampling with a userspace page cache and Direct I/O

A controlled comparison of the existing Linux memory-mapped reader (mmap) and a bounded DiskGraph page cache that bypasses the Linux page cache with the Direct I/O flag (O_DIRECT) and submits concurrent reads through the Linux io_uring interface. The objective is higher end-to-end sampling throughput, not more storage operations in isolation.

01 · Page-cache bottleneck

Bypassing the page cache bottleneck

DiskGraph stores each table as compact node records in edges.bin. A separate in-memory offset index maps each table-local node identifier to the record's file and byte range. With mmap, reading that address is cheap while the file page is in RAM. If the page is absent, the processor triggers a page fault and that sampling worker waits while the Linux kernel reads the page from storage.

How DiskGraph finds the graph data for a node

Each sampling hop starts with a set of node IDs called the sampling frontier. For every ID, the in-memory offset index for the packed graph format gives the start and end of its record. The sampler reads the relationship counts, chooses up to the requested number of neighbors per relationship (the fanout), and fetches only the byte ranges containing those neighbors and any requested node features.

Why batching reads and caching them in DiskGraph improve throughput

The Linux page cache is a general shared facility: it supports unrelated files and processes, reclaim, readahead, dirty data, writeback, and memory-control policy. DiskGraph's index is immutable and already has its own address map. Its cache only needs to retain fixed-size read-only blocks and protect them while a batch decodes data.

Planning the reads before touching the data lets DiskGraph avoid duplicate page reads within one sampling hop, combine adjacent ranges that are contiguous in the graph file, and control how many reads remain in flight. The userspace cache separately preserves blocks that are likely to be reused and gives DiskGraph a fixed memory budget. The complete cached Direct I/O implementation is 2.24× faster for identity sampling when the index is in RAM, although that benchmark does not isolate cache lookup from the other changes in the path. Feature-heavy sampling is tied or slightly slower in RAM, so the result depends on how much non-I/O work each sampled node requires.

02 · Userspace page-cache design

How the new page cache works

The offset index continues to map every node ID to its record's file and byte range. The new cache does not index nodes and does not replace graph decoding. It stores immutable 4 KiB blocks identified by graph file and page number. Once initialized, a fixed number of entries bounds the cache's memory use; the cache fills as newly read blocks are stored.

Mapping graph records to cache blocks

Map node byte ranges to cache blocks with the existing offset index

The sampler already knows each requested byte range. It divides the byte offset by 4 KiB to identify the cache blocks containing that data, so the cache does not need a separate hash-table entry for every graph node.

key = (file_id, byte_offset ÷ 4096)

A 4-byte directory entry for every node in the full identity graph would consume roughly 293 GiB. The cache instead keeps metadata only for blocks currently stored in RAM.

Cache lookup structure

A cache lookup checks four entries for the requested 4 KiB block

The graph file and page number select one cache bucket. In this benchmark configuration, each bucket contains four candidate entries. Every entry stores the identifiers needed to validate a read-only block and a reader count that prevents replacement while the sampler decodes it.

entry 1block identifierreader count and load statevalid byte count4 KiB graph data
entry 2matching block identifierone active reader4,096 valid bytesrequested graph data
entry 3block identifierreader count and load statevalid byte count4 KiB graph data
entry 4block identifierreader count and load statevalid byte count4 KiB graph data

The cache first compares block identifiers. It reserves a matching entry for the reader, then verifies the identifier again before returning data. An entry cannot be replaced until every active reader finishes. A one-bit recently-used marker gives active blocks a second chance before replacement without maintaining a shared least-recently-used list.

Cache hit

Cache hits return data without entering the kernel

1Compute the page key from the byte range and check the four entries in one cache bucket.
2Increment the matching entry's reader count and recheck its block identifier so replacement cannot race the read.
3Decode the requested edge or feature bytes directly from the cache's preallocated memory, then decrement the reader count.

Cache data and bookkeeping memory are preallocated. The remaining steady-state allocations create temporary structures used to plan a batch and its read phases; the sampler does not allocate once per node or cache hit.

Cache miss

Cache misses are deduplicated and submitted as a read batch

1Reserve an available cache entry while its block is loaded, and remove duplicate page requests from the sampling hop.
2Group reads by graph file and I/O submission worker. Adjacent byte ranges in the same file can share one larger read when the offset index confirms they are contiguous.
3Submit aligned O_DIRECT reads through 32 fixed I/O workers, each using its own io_uring queue, then wait once for the read batch.
4Copy each completed read into its reserved cache entry, mark the block available, decode the requested bytes, and reuse the temporary aligned read buffer.

If a cache bucket has no entry that is safe to replace, DiskGraph uses the completed read for the current request without retaining it in the cache. A busy cache can therefore reduce the hit rate, but it does not prevent the request from completing.

03 · Benchmark results

Sampling throughput by workload and graph size

Within each comparison, mmap and cached Direct I/O started from the same node IDs and used the same graph-sampling configuration, random seed, batch size, and matching output checksum. Each I/O method was tuned for its highest sustained sampled nodes per second. Absolute rates should not be compared across workloads: identity and Pinterest return graph edges, while commerce also reads and materializes node features.

Why throughput improved · unpruned Pinterest graph

Achieved 2.44× more throughput on the Pinterest graph

The 3,200 GiB index is 4.31× larger than host RAM, and both I/O methods perform sustained physical reads. They issue almost the same number of reads per sampled node: 0.109 for mmap and 0.108 for cached Direct I/O. The difference is storage concurrency. Cached Direct I/O raises the average number of reads in flight across all six drives from 169 to 917, the physical read rate from 1.290 million to 3.115 million operations per second, and sampling throughput from 11.799 million to 28.731 million nodes/s. It also uses 85.1% less CPU time per sampled node.

How sampling throughput changes as the graph index grows beyond RAM

Identity performs little work beyond graph-edge lookup, so the overhead of the DiskGraph cache is a larger fraction of total work. Commerce spends much more time decoding and materializing features; when its index fits in RAM, cached Direct I/O is tied with or slightly slower than mmap. As either index grows beyond RAM, the ability to keep many SSD reads in flight becomes the main performance difference.

Achieved 5.79× more throughput on the 12,449 GiB commerce index

On the Threadripper machine, the 12,449 GiB commerce index was 24.75× larger than its 502.97 GiB of RAM. Cached Direct I/O was 5.793× faster than mmap, used 40.5% fewer CPU cores on average, and consumed 89.7% less CPU time per sampled node. The run was limited by read bandwidth. 04 · Cache block size

Evaluating 1 KiB and 512 B cache blocks

The SSD read size and the amount retained in RAM are separate choices. Direct I/O can continue reading aligned 4 KiB blocks while the cache stores only the 1 KiB or 512 B regions used by the sampler. This matters most for the identity graph, where average encoded edge lists range from 5.7 B to 246.5 B, excluding record headers and encoded node-feature rows.

Proposed smaller-block cache

Read 4 KiB from SSD and cache only the requested sub-blocks

The in-memory offset index already maps a node ID to a file and byte range, so smaller cache blocks do not require another node directory. Requests for multiple regions within the same 4 KiB SSD block must still be combined into one physical read.

A 4-byte cache-directory entry for every one of the 78.6 billion nodes would use about 293 GiB. Using the existing offset lookup and storing metadata only for blocks currently in the cache avoids that cost.

At 512 B, cache bookkeeping uses 5.6 GiB more memory than the 4 KiB design and memory available for graph data falls by 2.2%. That trade is useful only if it prevents enough nearby bytes that are never reused from occupying the cache. The 155.5 GiB in-memory offset index is unchanged in all three cases.

Model estimate · not measured performance

The model estimates 8.5% more throughput with 512 B cache blocks

The measured full identity run provides the baseline: a 4,083.8 GiB index on a 503 GiB host, a 256 GiB data cache, a 17.09% cache hit rate, and 104.44 million sampled nodes/s. The equal-memory sensitivity model assumes a mixture of frequently reused and uniformly requested byte regions while holding the device limit of 6.123 million read operations per second and cache lookups per sampled node constant.

The existing identity generator distributes node requests uniformly. Coordinate cache size with pending edge-format changes

Choose cache block size after finalizing the edge layout

Planned formats that store association and time-series edges with their owning nodes will change both the bytes per record and the byte ranges read by the sampler. Capture a new request trace after the edge format is settled, then choose the cache block size from that access pattern. Do not multiply speedups measured separately for the edge format and the I/O path; benchmark both changes together.

05 · Next steps

Work required to integrate cached Direct I/O into production training

The sampler benchmarks show that cached Direct I/O can keep the storage array busy and increase sampled nodes per second. They do not show that Kumo training becomes faster. The next phase should integrate one production training workflow, measure the entire pipeline, and retain the existing mmap implementation as an I/O option selected when the process starts for comparison and rollback.

Integrate the Direct I/O reader with the production sampler

Put the new file-reading implementation behind the normal graph-loading and sampling interfaces, then test training-table generation, data loading, feature materialization, cancellation, graph shutdown, and error propagation. Cache size must be derived from total process memory after accounting for the offset index, in-progress sampling node sets, output data, allocator headroom, and memory reserved for the operating system—not from free RAM alone.

Measure one Kumo 3 or relational deep learning workload end to end

Kumo 3 and the relational deep learning (RDL) training pipeline are candidate production users of this I/O path. Use a representative production model configuration and a dataset larger than RAM. Require identical sampled output and model inputs, then compare training examples per second, GPU utilization, CPU time per example, storage traffic, peak memory, and recovery behavior. The acceptance criterion is shorter training time without a regression in the comparison workload whose index fits in RAM.

Evaluate cache block size after the edge format is finalized

Land or freeze the edge-layout changes, capture the production byte-range trace, and simulate each cache block size before implementing blocks smaller than 4 KiB. Retain 4 KiB if the estimated reduction in physical reads does not cover the smaller-block design's additional cache-entry metadata, boundary handling, and CPU work.

Compare CPU caching with GPU-direct graph loading

For Kumo 3 or RDL, the Direct I/O implementation can serve graph data from a cache in CPU memory. As a separate experiment, compare a cached CPU data source for NVIDIA cuGraph and WholeGraph with uncached NVIDIA GPUDirect Storage (GDS) before SCADA, the planned long-term graph-storage system, is broadly available. CPU caching can help when popular graph regions are reused often enough to produce frequent RAM-cache hits. GDS is the relevant comparison and may be preferable when most data is read once and the workload is limited by read bandwidth.

Select and assign the first production integration

Choose one target—the Kumo 3 sampler, RDL training-table path, or a WholeGraph bridge—and verify identical sampler output along with the same CPU, memory, and storage measurements used here. Until that work is complete, this remains a benchmark-only I/O implementation rather than a production-ready storage component.
